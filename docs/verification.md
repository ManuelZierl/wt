# Verification

The acceptance suite exercises the CLI through the built `wt` binary and validates real submissions, disk manifests, fixture files, plans, and command results with the Rust `jsonschema` crate.

Run the focused suite with:

```sh
cargo test -p wt-cli --test acceptance
```

The suite includes the decimal TSX vectors under `examples/template-number-decimal-step/`, including the retained `invalid-tsx.tsx` demanded-parse case. A demanded helper parse failure must be reported as incomplete analysis; a guarded helper call must not parse the file.

The optional shared-query workload is ignored by default. It creates 10,000 files containing 104,860,000 bytes (slightly over 100 MiB) and runs 25, 100, and 1,000 simple rules. It reports measured work counts and asserts no timing threshold:

```sh
cargo test -p wt-cli --release --locked --test acceptance performance_matrix_work_counts_10k_files_100mib_and_25_100_1000_rules -- --ignored --nocapture
```

## Executed shared-query workload

Executed on Linux x86-64, kernel 7.0.0-31-generic, Intel Core i7-6600U (four logical CPUs), Rust 1.94.0, release profile. Backend versions are pinned in `Cargo.lock` (Rhai 1.26.1, regex 1.12.2, tree-sitter 0.24.7). Persistent caches were bypassed, optimizer was `auto`, and the default admitted three workers.

| Rules | Source reads | Bytes hashed | Logical query requests | Physical text evaluations | Shared-result hits |
|---:|---:|---:|---:|---:|---:|
| 25 | 10,000 | 104,860,000 | 250,000 | 10,000 | 240,000 |
| 100 | 10,000 | 104,860,000 | 1,000,000 | 10,000 | 990,000 |
| 1,000 | 10,000 | 104,860,000 | 10,000,000 | 10,000 | 9,990,000 |

All three scans completed without findings or analysis errors. The combined test took 954.18 seconds, including corpus/package creation and all three scans; this is not an isolated per-scan timing. CPU time and peak RSS were not measured. The corpus and rule definitions are generated by the test itself. A subsequent accounting correction changed logical step/native-byte counters; the table records source/query work rather than those corrected counters.

This initial run covers only the identical-text-query scenario. The later extension below measures some warm-cache and mutation cases; the full distinct-pattern, JSX-scale, and repository matrix remains unmeasured. Smaller automated tests cover regex sharing, parser sharing, cache invalidation, and reference/parallel result equivalence.

### Revision-3 follow-up run (2026-09-24)

The same ignored release workload was rerun on Linux 7.0.0-31-generic x86-64,
Rust 1.94.0, four available logical CPUs and three admitted workers after the
schema-3 runtime/memory and result-projection changes. The final invocation
was `cargo test -p wt-cli --release --test acceptance performance_matrix_work_counts_10k_files_100mib_and_25_100_1000_rules -- --ignored --nocapture`.
It passed all 25/100/1,000-rule scans. Each had 10,000 source reads,
104,860,000 source bytes hashed and 10,000 physical text evaluations;
logical requests and shared hits were respectively 250,000/240,000,
1,000,000/990,000 and 10,000,000/9,990,000. The test process took 916.99
seconds including corpus and rule creation and all scans; compilation before
the test took a further 32.66 seconds. Per-scan wall/CPU time, peak RSS,
warm-cache results, other workload types and macOS/Windows results were not
measured. An initial attempt failed because new stats fields were not
projected out of strict protocol 2; this was corrected and the full workload
passed on rerun. It is not full revision-3 performance qualification.

The ignored release-mode component benchmark was also rerun with
`cargo test -p wt-runtime --release --test shared_query_performance -- --ignored --nocapture`.
Its three-repeat median times were 0.01983 seconds (whole-file text), 0.07927
seconds (shared regex) and 1.54260 seconds (many matches), for 32 files and
128 consumers. These measurements exclude repository discovery, worker IPC,
compilation and persistent caches; they are not end-to-end scan timings.

### Isolated-cache workload extension (2026-09-24)

The current release-mode benchmark creates a unique, 104,860,000-byte corpus
and isolates the persistent cache under its temporary global directory. It
measures each `wt check` invocation separately with a monotonic clock, including
process startup, discovery, rule loading, hashing, worker work and output.

| Scenario | Rules | Elapsed ms | Raw cache hits / misses | Physical text evaluations |
|---|---:|---:|---:|---:|
| Cold, cache disabled | 25 | 41,612 | disabled | 10,000 |
| Seed persistent cache | 25 | 64,566 | 0 / 250,000 | 10,000 |
| Warm unchanged full scan | 25 | 6,949 | 250,000 / 0 | 0 |
| One file changed, full scan | 25 | 6,614 | 249,975 / 25 | 1 |
| One rule added | 26 | 12,807 | 250,000 / 10,000 | 10,000 |
| New rule edited | 26 | 11,127 | 250,000 / 10,000 | 10,000 |
| Cold, cache disabled | 100 | 87,901 | disabled | 10,000 |
| Cold, cache disabled | 1,000 | 789,171 | disabled | 10,000 |

All invocations completed with zero findings or analysis errors and read/hashed
10,000 source snapshots each. The full test, including creation and every
invocation, took 1,023.88 seconds. These are individual measurements from one
Linux machine, not stability thresholds or comparisons with other products.
The profiler did not record CPU time or peak RSS. Distinct-pattern, JSX-assisted,
repository reduction, deletion, `--changed`, and full auto/off/serial/parallel
large-corpus variants remain unmeasured.

The same isolated-cache benchmark passed again on 2026-09-25 against the final
candidate source with `--release --locked`. Cold no-cache scans took 25,037 ms
(25 rules), 83,997 ms (100 rules) and 835,689 ms (1,000 rules). For 25 rules,
cache seeding took 47,167 ms, warm unchanged 6,069 ms, one-file-changed 5,957
ms, one-rule-added 9,877 ms, and one-rule-edited 10,272 ms. Work-count and
cache-hit/miss assertions remained unchanged; the complete test took 1,027.05
seconds. The edited-rule invocation reported 6,352 successful cache writes
for 10,000 misses; it still completed all rule/file work, but this run does
not establish that all optional cache writes succeeded. The benchmark did not
record the cause of the unwritten entries.
